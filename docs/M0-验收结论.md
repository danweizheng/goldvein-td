## 1. 三项验收标准的独立验证结果

### ✅ 证据 1：确定性内核 —— 1x / 2x / 4x 状态哈希一致

**命令**：`pnpm exec vitest run src/sim/__tests__/determinism.spec.ts --reporter=verbose`
**结果**：`Test Files 1 passed` / `Tests 10 passed` / `exit=0`

关键输出（三种驱动方式跑同一场景，比对 `hashWorld()`）：

```
用例 1（空指令，N=10800 = 180s 游戏时间）
  hashes c2bebe7c94d642a8 / c2bebe7c94d642a8 / c2bebe7c94d642a8
用例 2（带指令脚本，N=10800）
  hashes b2191c413834d02f / b2191c413834d02f / b2191c413834d02f
  events 25749 / 25749 / 25749          ← 事件流也逐条一致
用例 3（渲染层实际用法 advanceFrame(speed)，tick=1200）
  hashes b4ec2209e26820af / b4ec2209e26820af / b4ec2209e26820af
```

**超出要求的部分（都是加分项）**：

| 附加验证 | 说明 |
|---|---|
| 用例 4 定点约束 | 递归扫描世界状态，断言**所有数值都是整数**（`collectNonInteger(w) === []`），无浮点混入 |
| 用例 5 契约形状 | 快照字段齐全 + **投射物池容量恰为 500** + 快照对象被复用（无每帧新对象） |
| 用例 6 可重建性 | 同 seed + 同指令流 → 哈希完全一致，**回放与挑战码分享的前提成立** |
| **负对照** | 换 seed → 哈希不同（`expect(hashWorld(other)).not.toBe(ha)`），证明哈希有区分度而非恒等 |
| 实测 N | 我建议 N=3600（60s），实际用了 **N=10800（180s）**，覆盖了 4+ 波与 25749 条事件 |

> **判定：这是 M0 最重要的一条结论，证据强度超出预期。** 倍速不走 `dt` 而是走固定 1/60s 步长、重复调用 `step`/`tickMany` 的实现方式得到验证。

### ⚠️ 证据 2：250 敌人 + 500 投射物 60fps —— **逻辑通过，渲染未验证**

```
── 逻辑路径：压力场景：250 敌人 + 500 投射物（35 压力塔）
   tick 数          36000  (= 600.0s 游戏时间)
   单 tick 耗时     avg 0.702 ms | p50 0.747 | p95 0.856 | p99 0.983 | max 2.284
   帧预算占用       4.211% of 16.67ms   →  60Hz 逻辑可达成
   峰值同屏         271 敌人 | 500 投射物
   内存峰值         heapUsed 20.9 MB | RSS 81.4 MB
   状态哈希         24b42368e35e900c

── 渲染路径（浏览器实测）
   ⚠️  无法验证：浏览器基准页未在 90s 内输出 BENCH_RESULT
```

**通过的部分**：逻辑路径只用掉 **4.2% 的帧预算**（avg 0.702ms / 16.67ms），同屏峰值 **271 敌人 + 500 投射物**，堆内存 20.9MB。这比策划案 1.5 的指标（60fps @ i5-8250U、内存 ≤200MB）**宽裕一个数量级**。

**渲染侧的后续进展（`engine-dev` 在收尾轮跑通）**：

它**拒绝了用 Node mock 伪造 FPS**（"Node 里没有光栅器/GPU，任何 FPS 都只是在测我自己的假实现"），改用 CDP over WebSocket 驱动 headless Edge 跑真浏览器基准，实测：

| 场景 | avg FPS | 最低（500ms 窗） | p95 帧时长 | 掉帧率(>16.67ms) |
|---|---|---|---|---|
| `sim+render` | **2901** | 2761 | **0.4 ms** | **0.00%** |
| `render-only`（模拟暂停） | 3052 | — | — | — |
| `text-storm`（每帧强推 40 条飘字压满池） | 2093 | — | — | 0.00% |

池峰值 `{"enemy":250,"projectile":500,"text":300}` —— **三个池都跑到容量上限**，同屏 271 敌人 + 500 投射物 + 300 飘字。

**必须按"未在目标硬件验证"记账的三条限制**（`engine-dev` 主动提出，主策划采纳）：

1. **帧率未锁 vsync**，所以这些数字是**余量**（只用了约 3% 帧预算）而非体验帧率。
2. **本机 GL 报 `WebKit / WebKit WebGL`（headless 虚拟光栅），不是验收点名的 i5-8250U 核显。目标硬件无法验证。**
3. **该基准间歇性失败**：3 次尝试里 1 次 90s 超时无输出，未加重试循环。

> **因此 M0 指标 ① 的记账方式**：逻辑侧 ✅ 通过（且有充分余量）；渲染侧 ⚠️ **"在 headless 虚拟光栅、未锁帧率下达成的余量数据"，目标硬件未验证**。**不要按"通过"记账。**

### ✅ 证据 3：像素 NEAREST 无糊边 —— **带负对照的受控实验**

```
integer-8x   / NEAREST【出货配置】: 精确颜色数=3  混色像素=0     描边段长=[8,8]   主体段长=[112] → crisp
fractional-7.37x / NEAREST       : 精确颜色数=3  混色像素=0     描边段长=[7,7]   主体段长=[104] → shimmer
integer-8x   / LINEAR【对照组】   : 精确颜色数=77 混色像素=5564  描边段长=[]      主体段长=[128] → blurry
```

**这不是"跑了一下看起来没问题"，是三个对照组的设计**：

| 组 | 作用 | 结论 |
|---|---|---|
| 整数倍 + NEAREST（出货配置） | 待验证对象 | 混色像素 **0**，描边段长 [8,8] 均匀 → **crisp** ✅ |
| 整数倍 + LINEAR | **负对照** | 混色像素 **5564**、77 种颜色 → 证明"混色检测器"本身有效，不是空测试 |
| 非整数倍 7.37x + NEAREST | **边界对照组** | 混色像素 0 但描边段长 [7,7] → **像素大小不均匀（shimmer）**，这是"必须整数倍缩放"的直接证据 |

> 第三组是**超出验收要求的有价值发现**：NEAREST 并不能单独保证清晰度，**必须同时约束整数倍相机缩放**。这条已写进 AGENTS.md 的渲染优化清单（第 5 条）。

## 4. 门禁判定与下一步

**M0 门禁：通过。** 三项标准中 2 项完全验证、1 项部分验证且风险已被量化（逻辑仅占 4.2% 预算，渲染余量充足）。

**注意**：M0 只验证**技术可行性**。策划案里真正的 Go/No-Go 是 **G1（M1 结束）**——即"窃金手感是否成立"与"军训系卡位差额是否 ≥25%"。**M0 通过不代表 G1 会通过。**

**`data-arch` 找出了主策划策划案里的 4 处实质错误**，其中 1 处是**重犯**：

| 错误 | 性质 |
|---|---|

**方法论教训（已写入风险表第 4 项）**：主策划用**同一张错表**做了"反推验证"，等于自己验自己，因此 §5.2 与 §5.5 的错误互相掩护、全部通过。

**结论：独立交叉审查不是冗余，是必需品。** 这也直接决定了批次 3 保留 `qa-verifier`，且它的 KPI 必须是「找到问题」而非「通过」。
