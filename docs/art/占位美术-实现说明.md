## 2. 实现后的编码表（精确到像素）

### 2.1 塔（48×48，锚点（24, 43））

```
line → 轮廓         thief ◆diamond  archer ▲triangle  mage ⬢hexagon  drill ■square
                    beauty ●circle  cannon ⬣octagon   worker ▣notchedSquare
                    sprite ∴dotCluster                 tech ✚cross
tier → 底部齿数      底座(y36–42) 上 tier 个 4×4 亮块（齿距 2px）
tier ≥ 3 → 轮廓线宽  1px → 2px
本体内 2–4 颗 1px 暗痕 = 单位指纹（id 哈希）→ 保证"两个不同 id 绝不撞图"
```

- 本体半径 14px（`worker` 因"小方块"语义取 10px 系数 0.72；`drill` 0.93），中心 `(24, 19)`。
- 塔的颜色只在**同系**里变化，跨系区分靠轮廓；灰度下 9 个塔系颜色的亮度高度重叠
  （见 §6），因此**轮廓是主通道，颜色只是冗余**。

### 2.2 敌人（32 / 48 / 96，锚点 = 帧中心 x，帧中心 y + 标称半径 + 1）

```
护甲 → 边框（距本体 2px 起，距离 1 留 1px 空隙）
    light      虚线 1px（2-2 交替，沿 x+y）        实测最内圈上色率 0.57（有断口）
    medium     实线 1px                            实测 1.00
    heavy      实线 2px                            实测 1.00，且距离 3 也满
    fortified  双层：2px 内圈 + 1px 间隔 + 1px 外圈（伸到距离 5）
    divine     实线 2px + 四角金色刻痕（4 角各 2px 厚 L 形）
flying    → 本体两侧亮色翼痕（并入本体掩码，边框会包住它）+ 本体整体上移，
            地面线以上留白。**长度/留白按帧尺寸等比放大**：
            32 帧 → 翼 3px、留白 2px ｜ 48 帧 → 6px / 4px ｜ 96 帧 → 9px / 6px
isBoss    → 距离 7–8px 的金色实环（在护甲边框外侧，留 1px 空隙）
精英      → 右上角 7×7 金色菱形星（25px，可数）
stealResist > 0    → 左下角 5×8 挂锁（亮色锁身 + 1px 暗描边），按帧尺寸缩放
stealResist = 1000 → 挂锁 + 2px 斜杠（把锁切成两半）+ 斜杠外侧 1px 亮边
```

> **为什么标记要随帧尺寸缩放**：方案 §2.2/§8 的尺寸本身就是 32px 基准（普通敌 32、精英 48、
> BOSS 96）。若把「2px 留白」「3px 翼痕」写成固定像素，96 帧 BOSS 的标记在比例上只有普通怪的
> 1/3 —— 实测（改前）：ascendant 翼痕带只比地面态多 **9px**，留白带甚至**反向**（飞行态 65px >
> 地面态 56px，因为它自己的金环把 2px 空隙占满了）。改为等比放大后：翼痕带 **+53px**、
> 留白带 273→198px（真的空出来了）。挂锁/星点本来就按 `markScaleFor` 缩放，翼痕与留白是漏的。
> 若主策划要求逐字固定 2px，改 `marks.ts` 的 `flyingGapFor`/`addWings` 各一处即可回退。

- 本体直径 = 帧宽 / 2：16 / 24 / 48px。因此 **BOSS 本体 48px = 普通敌帧宽 32 的 ×1.5**
  （对上方案 §2.2「尺寸 ×1.5」），而帧 96×96 是给金环与留白用的（对上方案 §8）。
- 本体上另有：护甲色圆芯（半径 r/3）、2×2 亮色眼、1–3 颗 id 哈希决定的小暗纹。
  这些只负责"像个体"与"唯一性"，不承载语义。

### 2.3 状态帧（方案 §2.3，程序化变形）

| 精灵 | 状态 | 实现 |
|---|---|---|
| 塔 | `idle` | 基准姿态（呼吸浮动留给渲染层 ±1px，不占帧） |
| 塔 | `attack` | 本体层沿朝向 +1px + 中心 2×2 白闪 + 出膛口 2×2 亮点 |
| 塔 | `upgrade` | 本体外扩 1px 的金色圆环 |
| 敌 | `idle` | 基准 |
| 敌 | `walk` | 整体 −1px（周期 20 tick 的交替位留给渲染层） |

### 2.4 条（方案 §2.4，只输出规格）

| 条 | 位置（相对锚点） | 宽 | 高 | 颜色 | 重要度 |
|---|---|---|---|---|---|
| HP | 精灵可视顶边上 2px | 本体宽 | 1px | 按比例 红→黄→绿 | 1 |
| **钱包** | HP 下方 1px | 本体宽 | 1px | 金 `#ffc832` + 暗底槽 + **1px 暗外圈** | **2（招牌）** |
| 阻挡 | 着地点下方 1px | 1px | 1px | 白 | 1 |

规格在 `BAR_SPECS`，布局由 `layoutBars(spriteSize, anchorX, anchorY)` 计算
（**按本体可视区推导，不按帧高** —— 否则 96 帧的 BOSS 会把血条顶到离本体 24px 之外）。

## 3. 接线约定（交给 `engine-dev` / 主策划）

```ts
// 现在
const source: SpriteSource = new ProceduralSpriteSource(content); // content 来自 src/data
// 接真实美术时
const source: SpriteSource = new AtlasSpriteSource(atlasJson, atlasPng); // 调用方一行不改

source.atlas.imageWidth / imageHeight / frames[`${id}:${state}`] / meta
source.render()  // Uint8ClampedArray，RGBA 行优先，长度 = w*h*4
```

渲染层需要知道的 3 件事（**都不是约定之外的东西，但接错会出问题**）：

1. `FrameRef.anchorX/anchorY` 是**帧内局部坐标**（不是图集绝对坐标）。
   当前值：塔 `(24, 43)`；普通敌 `(16, 25)`；精英 `(24, 37)`；BOSS `(48, 73)`。
2. **必须 NEAREST + 整数倍缩放**（M0 结论）。图集尺寸 1024×512，是 2 的幂。
3. **BOSS 帧是 96×96，但本体只有 48px**。若渲染层把"帧"缩放到统一屏幕尺寸，
   BOSS 会显得**比普通怪还小**。正确做法是按 `anchorY` 对齐地面线、按原始像素 1:1 绘制。
   ⚠️ 这一条**没有在游戏里验证过**（本模块不跑渲染），请接线后实测一眼。

## 6. 客观测量（**通道隔离**后到底差多少）

### 6.1 采样区必须等于通道真正所在的区域（这一节是踩坑记录）

| 通道 | 唯一正确的采样区 | 用错的区域会怎样（实测） |
|---|---|---|
| 护甲 | 到本体切比雪夫距离 `[2,5]` 的**环带** ∪ 四角刻痕区 | 帧外圈 2px 矩形框：**0 个实体像素** → 差异恒为 0（精灵本体在帧中央） |
| 品阶 | 底座上那 9×9 的齿区 | 算整帧差异：被本体形状淹没 |
| 飞行·留白 | 飞行态机身下方那几行 | 帧最低 6 行：两种状态的机身都不在那里 → 只差 5px |
| 飞行·翼痕 | 地面态本体水平包围盒之外、机身中线 ±2 行 | 「离本体 > 5px 的环外区」：对角方向的切比雪夫距离更短，翼痕外缘恰好落在距离 5 → 0px |
| 品阶/免疫 | （见 §7：这两条是**亮度图案**通道，不是剪影通道） | 用 alpha 剪影判据会得到 0 |

**教训**：`diff(整只精灵)` 是个**永远好看**的数字，它可能完全由无关通道贡献。
断言必须窄到只覆盖被测属性，并配**负对照**证明它没测到别的东西。

## 7. 已知缺口（我做不到 / 没验证的）

1. **阻挡名额数无法在 1×1 里表达**。方案 §2.4 规定阻挡条是 `1×1` 白点，
   只能表达"这个敌人被挡住了"，表达不出 `blockUsed/block`（军训系 3/6 名额）。
   建议：白点保留，名额数走详情面板或"阻挡点附近的小刻度"（需主策划定）。
2. **窃金抗性的"程度"只有二值**。挂锁 = 有抗性，挂锁 + 斜杠 = 免疫；
   `stealResist: 300` 与 `700` 画的是同一张图。建议数值只在详情面板显示。
3. **"抗性 700 vs 免疫 1000"是全部通道里最弱的一条**（32×32 下灰度只差 18px）——
   **但这是伪问题**：700 只出现在 `merchant_lock`（32×32），1000 只出现在
   `ascendant`（96×96），两者永远不会同框比较。按主策划裁决：**不改设计**，登记 M6。
4. **精英的判定是推断的**。`src/data/enemies.json` **没有** `isElite` 字段，
   当前规则集中在 `content.inferElite`（显式字段 > id 前缀 `elite` > `dodge > 0`），
   实际只命中 `elite_assassin`。建议 `data-arch` 补一个显式字段（契约 §7 的快照里也没有它）。
5. **未见真人目视，且本 agent 与主策划的模型都不支持图像输入**。
   所有结论都是**逐像素测量 + ASCII 预览 + 对照**得出的，不是"看着挺好"。
   功能性验收（某通道有没有像素、灰度/色盲下差多少）已经可以靠测量闭环；
   **审美取舍（好不好看、够不够醒目）仍然缺一个能看图的人**。这一条必须写清楚：
   不要再假设"有人会顺手看一眼"。
6. **渲染接线未验证**：`src/render/**` 尚未消费本模块，BOSS 96 帧的显示比例、
   条状 UI 在真实战场背景上的可读性都**没在游戏里跑过**。
7. **塔的"呼吸/走位"由渲染层实现**：`idle` 帧不含 ±1px 浮动、`walk` 帧只含 −1px 位移，
   周期（30 tick / 20 tick）需要渲染层按 tick 做，帧本身是静态的。
8. **能力边界（不是缺口，是事实）**：96 帧 BOSS 的"机身中线跨度"被神圣甲的四角刻痕
   顶满到整帧宽（地面/飞行都是 96px）—— 该指标对 BOSS 无效，必须改用"翼痕带实体数"。
   测试里已把这条钉住，防止有人再用跨度去判 BOSS 的飞行。
