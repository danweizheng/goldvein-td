## 1. 为什么需要这份文件

批次 1 有三个 agent 并行工作。他们看不到彼此的上下文，也看不到主策划的对话。**唯一能防止他们互相踩的东西就是这份契约**——它把「谁定义什么、谁消费什么」写死。

三条硬规则：

1. **定义方独有**：每个类型只有一个所有者，别人只读。
2. **消费者不发明字段**：需要新字段 → 提给主策划 → 升版本 → 所有人同步。
3. **M0 阶段解耦**：`engine-dev` 的确定性内核与性能基准**不得依赖 `src/data/`**，用内联合成夹具（synthetic fixture）。真实数据集成放在 M1。这是为了避免两个 agent 在 M0 互相阻塞。

## 2. 定点数约定（全局）

| 项 | 约定 |
|---|---|
| 缩放因子 | `FIXED_SCALE = 1000` |
| 类型别名 | `export type Fixed = number;` —— **始终是整数**，真实值 = `Fixed / 1000` |
| 适用范围 | **模拟层一切数值**：位置、速度、伤害、窃金额、**金币、木材**、移速倍率、千分比加成 |
| 例外 | 纯计数用普通整数：tick 序号、塔/敌人 id、波次号、阻挡名额、数组下标 |
| 显示 | UI 层显示金币时 `Math.floor(gold / 1000)` |
| 禁止 | 模拟层内任何 `/` 运算的结果不得直接进入状态（必须先取整）。推荐用 `mulDiv(a, b, c)` 保持精度 |

> **为什么金币也走定点**：窃金是**每次攻击结算一次**的细粒度收入（一局数千次），若每次取整到整数金币，舍入误差会系统性累积。统一走定点可消除这类漂移，也让「1x/2x/4x 状态哈希一致」这条验收标准更容易成立。

```ts
// src/sim/fixed.ts —— engine-dev 所有者
export type Fixed = number;
export const FIXED_SCALE = 1000;

/** 定点乘：返回 (a * b) / FIXED_SCALE，结果向零取整 */
export function fmul(a: Fixed, b: Fixed): Fixed;
/** 定点除：返回 (a * FIXED_SCALE) / b，结果向零取整 */
export function fdiv(a: Fixed, b: Fixed): Fixed;
/** 通用三参数乘除，用于避免中间溢出 */
export function mulDiv(a: number, b: number, c: number): number;
/** 千分比应用：(base * pct) / 1000 */
export function applyPct(base: Fixed, pct: Fixed): Fixed;
```

### 3.3 `constants.json`（本契约新增的第 8 张表）

**为什么需要**：策划案 §4.1.2 / §4.3 / §5.1 里有大量公式常量（血量指数 1.38、钱包指数 1.29、等级系数数组、克制矩阵、压缩系数…）。若让 `engine-dev` 把它们写死在代码里，就违反了 AGENTS.md 铁律 5（数据驱动），策划改平衡必须改代码。

**契约要求**：`constants.json` 必须覆盖 **策划案中所有出现在公式里、且不属于 units/tech/relics/difficulty 的数值常量**。至少包含下列分组：

```ts
export interface BalanceConstants {
  // —— 时间 ——
  tickRate: number;                 // 60（普通整数，非定点）
  fixedScale: number;               // 1000（普通整数）

  // —— 成长曲线（§5.1）——
  baseHp: Fixed;                    // 40
  hpIndex: Fixed;                   // 1380 → 1.380
  baseWallet: Fixed;                // 10
  walletIndex: Fixed;               // 1290 → 1.290
  enemyCountBase: Fixed;            // 6
  enemyCountSlope: Fixed;           // 800 → 0.8

  // —— 窃金（§4.1.2）——
  levelMul: Fixed[];                // [1000, 1350, 1850, 2600, 3800]
  stealAtkCoef: Fixed;              // 20 → (1 + 0.02 × 攻击力)
  critRateBase: Fixed;              // 50 → 5%
  critRateCap: Fixed;               // 300 → 30%
  critMulBase: Fixed;               // 1500 → ×1.5
  critMulPerLevel: Fixed;           // 250 → +25%/级
  critMulCap: Fixed;                // 2750 → 275%
  stealResistDefault: Fixed;        // 0

  // —— 克制矩阵（§4.3）——
  counterMatrixStandard: Fixed[][]; // 5×5，行=攻击类型 列=护甲类型，定点倍率
  compressedFactor: Fixed;          // 500 → ×0.5
  compressedFloor: Fixed;           // 600 → 下限 0.6

  // —— 阻挡与卡位（§4.2.4）——
  haltPointStopDuration: Fixed;     // 600 → ★停顿点停留 0.6s

  // —— 结算（§4.7.1）——
  crystalDivisor: Fixed;            // 1000 → 累计窃金 / 1000
  difficultyCrystalMul: Record<string, Fixed>; // N1..N5 → 600/1000/1600/2400/3600

  // —— 建筑师技能（§4.1.4）——
  salaryCooldown: Fixed;            // 90000 → 90s
  salaryMultiplier: Fixed;          // 60000 → 60 × 基地产出
  brambleCooldown: Fixed;           // 120000 → 120s
  brambleDuration: Fixed;           // 3000 → 3s
}
```

> 具体键名允许 `data-arch` 微调（例如合并分组），但**每个策划案公式常量必须能在 `constants.json` 里找到**。交付时需附一份「公式常量 → 键名」对照表作为验证证据。

## 4. 模拟层公开 API（`engine-dev` 定义）

```ts
// src/sim/types.ts
import type { Fixed } from './fixed';

export interface Vec2 { x: Fixed; y: Fixed }

export interface RunConfig {
  seed: number;                                   // 可播种 RNG 种子
  difficultyId: 'N1' | 'N2' | 'N3' | 'N4' | 'N5';
  relics: Readonly<Record<string, number>>;       // 圣物 id → 等级
  techArchive: Readonly<Record<string, number>>;  // 科技 id → 存档等级
}

/** 可变世界状态。仅在 src/sim/** 内部可直接改字段。 */
export interface WorldState { /* engine-dev 设计 */ }

/** 只读视图。render / ui / balance 只能通过它读状态。 */
export interface WorldSnapshot { /* engine-dev 设计 */ }
```

```ts
// src/sim/world.ts
export function createWorld(cfg: RunConfig): WorldState;
export function snapshot(w: WorldState): WorldSnapshot;
/** 确定性哈希：用于验证 1x/2x/4x 结果一致。必须是纯函数、无浮点。 */
export function hashWorld(w: WorldState): string;

// src/sim/tick.ts
/** 前进恰好 1/60 秒。cmds 为本 tick 要应用的指令。 */
export function step(w: WorldState, cmds: readonly Command[]): void;
/** 前进 n 个 tick。用于倍速（2x = 每渲染帧调 2 次）。 */
export function tickMany(w: WorldState, n: number, cmds: readonly Command[]): void;
/** 取出并清空本 tick 产生的事件。 */
export function drainEvents(w: WorldState): SimEvent[];
```

### 4.1 倍速语义（重要）

倍速**不得**通过改 `dt` 实现——那会破坏定点数与确定性。正确做法：

```
1x → 每渲染帧调 step(w, cmds) 1 次
2x → 每渲染帧调 step(w, cmds) 2 次
4x → 每渲染帧调 step(w, cmds) 4 次
```

因此 `step` 永远走固定 `1/60s`，**不存在 dt 参数**。这也是「1x/2x/4x 状态哈希一致」这条验收标准的实现前提。

### 4.2 M0 解耦要求

M0 阶段 `engine-dev` **不得 `import` `src/data/**`**。确定性内核与性能基准用内联合成夹具（例如在 `tools/bench/fixture.ts` 里硬编码一组假单位/假敌人）。真实数据集成放 M1。

## 5. 指令契约（UI → Sim，冻结）

```ts
// src/sim/commands.ts —— engine-dev 定义；ui-dev 消费

export type Command =
  | { type: 'build';        unitId: string; cell: { x: number; y: number } }
  | { type: 'upgrade';      towerId: number }
  | { type: 'sell';         towerId: number }
  | { type: 'undo' }                                   // 10s 内撤销上一次建造
  | { type: 'relocate';     towerId: number; cell: { x: number; y: number } }  // 飞贼瞬移
  | { type: 'activateSkill'; skillId: 'salary' | 'bramble' | 'midas' }
  | { type: 'setSpeed';     speed: 1 | 2 | 4 }
  | { type: 'pause' }
  | { type: 'resume' }
  | { type: 'ascend' };                                // 主动蜕变（第 20 波后可用）
```

**约定**

- UI **不直接改状态**，只发 `Command`。这让撤销与回放天然成立。
- 指令在下一个 `step()` 中被应用。`build` 失败（位置非法/钱不够）时不抛异常，改为产出 `commandRejected` 事件。
- `setSpeed` / `pause` / `resume` 由外层循环消费，不进入 `step` 的状态机。

## 6. 事件契约（Sim → UI / Render / Balance，冻结）

```ts
// src/sim/events.ts —— engine-dev 定义；ui-dev / balance-eng 消费

export type SimEvent =
  | { type: 'steal';             towerId: number; enemyId: number; amount: Fixed; crit: boolean }
  | { type: 'kill';              enemyId: number; gold: Fixed; wood: Fixed }
  | { type: 'leak';              enemyId: number; livesLeft: number }
  | { type: 'waveStart';         wave: number }
  | { type: 'waveEnd';           wave: number; stats: WaveStats }
  | { type: 'build';             towerId: number; unitId: string }
  | { type: 'upgrade';           towerId: number; tier: number }
  | { type: 'sell';              towerId: number; refund: Fixed }
  | { type: 'blockExtraSteal';   towerId: number; amount: Fixed }   // ★ 军训系价值量化
  | { type: 'commandRejected';   command: Command; reason: string }
  | { type: 'gameOver';          result: 'win' | 'lose'; wave: number };

export interface WaveStats {
  wave: number;
  goldEarned: Fixed;        // 本波收入（窃金 + 击杀奖励）
  goldSpent: Fixed;         // 本波支出（建造 + 升级 + 科技）
  stolenTotal: Fixed;       // 本波实际窃取总额
  walletTotal: Fixed;       // 本波敌人钱包总量（理论上限）
  stealCoverage: Fixed;     // 千分比 = stolenTotal / walletTotal
  blockExtraSteal: Fixed;   // 其中因阻挡/卡位额外获得的部分
  leaks: number;            // 本波漏怪数（普通整数）
  towerCount: number;       // 本波结束时塔数量（普通整数）
}
```

### 6.1 `WaveStats` 是平衡验证的唯一数据源

策划案 [5.4 单局经济验收指标](窃金者TD-开发策划案-v0.2.md) 的每一条都必须能从 `WaveStats` 算出来：

| 验收指标 | 目标 | 由哪些字段算出 |
|---|---|---|
| 窃金覆盖率 | 65%–80% | `stealCoverage`（已是千分比，直接比 `650`–`800`） |
| 支出/收入比 | 80%–90% | `goldSpent / goldEarned` |
| 漏怪率 | < 2% | `leaks` 累计 / 敌人总数 |
| 波次末金币余量 | 波收入 10%–40% | `goldEarned − goldSpent` |
| **军训系存在性（Q1）** | `blockExtraSteal / stolenTotal ≥ 25%` | `blockExtraSteal / stolenTotal` |

> 因此 `blockExtraSteal` **必须**精确到「因阻挡才产生的增量窃取」，不能在 `waveEnd` 里用估算。实现建议：在 `steal` 结算时，若该敌人当前 `blockedBy != null`，则把这笔窃取额外计入 `blockExtraSteal`。

## 11. 音频资源契约（v0.1.1 增补）

> **增补原因**：v0.1 冻结时**漏掉了音频资源规范**——契约全文没有任何 audio / `.ogg` / volume 相关定义。`audio-curator` 已交付 40 个 CC0 音频文件，但 `engine-dev`（播放）与 `ui-dev`（音量条）接进来时无约定可依。本节由主策划补齐。

### 11.1 文件路径（扁平命名，冻结）

```
public/assets/audio/<id>.ogg
```

- **扁平结构，不分子目录**：40 个文件平铺，便于惰性加载与 Service Worker 预缓存。
- 格式统一 `.ogg`（Ogg Vorbis）。已独立验证 40/40 均为真 Ogg（魔数 `OggS`，无 HTML 伪装）。
- 命名前缀：`bgm_*` / `sfx_steal_*` / `sfx_combat_<塔系>_<动作>` / `sfx_ui_*` / `sfx_amb_*` / `sfx_win` / `sfx_lose`。

### 11.2 音频清单表（新增，`data-arch` 所有）

新增 `src/data/audio.json`，走与其他 8 张表相同的 Schema 门禁：

```ts
export interface AudioDef {
  id: string;              // = 文件名（不含扩展名），如 'bgm_menu'
  file: string;            // 相对 public/ 的路径，如 'assets/audio/bgm_menu.ogg'
  category: 'bgm' | 'sfx' | 'ambience';
  /** 混音通道：决定受哪条音量条控制 */
  bus: 'bgm' | 'sfx';
  /** 建议播放音量，千分比定点（1000 = 100%） */
  gain: Fixed;
  loop: boolean;           // bgm / ambience 通常 true
  /** 引擎侧交叉淡化。ambience 的循环接缝未处理，必须靠它掩盖 */
  fadeInMs?: number;
  fadeOutMs?: number;
  description: string;
}
```

**必须遵守的三条**：

1. `id` 集合与磁盘上 `public/assets/audio/*.ogg` **完全一一对应（不多不少）**。`pnpm validate-data` 必须增加这条**跨文件一致性校验**——只校验 JSON 内部一致性会漏掉「清单写了文件不存在」这类错误。
2. `category: 'ambience'` 的两条（`sfx_amb_vault` / `sfx_amb_street`）**必须设 `fadeInMs` / `fadeOutMs` ≥ 100**。这两个文件是从 123s / 119s 原曲截取的 30s 片段，接缝未做 crossfade，引擎不加淡化会在循环点听到咔哒声。
3. 混音总线只有 `bgm` 与 `sfx` 两条。**没有 `voice` 总线**（见 11.3）。

## 12. 配置表字段修订记录（v0.1.2）

> **背景**：M0 期间 `data-arch` 在按策划案播种数据时发现 3 处契约定义缺陷。经主策划裁决后已在其实现中生效，**本节把契约正文补齐，消除「文档与实现不一致」**。同时 §3.1 的条目数已随之更新。

### 12.1 `EnemyDef.bounty` → **`bountyRatio`**（破坏性改名）

```ts
// ❌ 旧（v0.1）：固定绝对值，无法随波次成长
bounty: { gold: number; wood: number };

// ✅ 新（v0.1.2）：占「该敌人当波钱包」的千分比
bountyRatio: { gold: Fixed; wood: Fixed };
```

**语义**：`实际击杀奖励 = 该敌人当波钱包 × bountyRatio / 1000`。**必须乘以当波钱包**，不是绝对值。

**为什么必须改**：契约 §3.2 与策划案 §14.1 原定义的 `bounty` 是固定绝对值，而策划案 §4.1.1 要求击杀奖励占总收入 **15–20%**。钱包曲线是逐波指数增长的，固定绝对值无法跟随——`data-arch` 实测若按字面实现，全局击杀奖励只有 **1,392 金 = 钱包总量的 0.04%**，与目标差 400 倍。字段名为 `gold` 却语义上是比率，是典型的集成陷阱（`engine-dev` 几乎必然会误实现）。

**当前取值**：全部 11 类敌人统一 `{ gold: 170, wood: 0 }`（= 17%，落在 15–20% 区间内）。**待标定。**

### 12.2 `UnitDef.aura` → **`auras: AuraDef[]`**（`aura` 已弃用）

```ts
// ❌ 旧（v0.1）：单对象，表达不了多效果光环
aura?: { kind: ...; value: Fixed; radius: Fixed; affects: ... };

// ✅ 新（v0.1.2）：数组，唯一规范字段
auras?: AuraDef[];

export interface AuraDef {
  kind: 'attackPct' | 'speedPct' | 'rangePct' | 'slowPct' | 'allPct'
      | 'stealPct'          // 训导主任：周围窃金塔效率 +
      | 'stealResistDebuff'; // 训导主任：被阻挡敌人窃金抗性 −
  value: Fixed;             // 千分比
  radius: Fixed;            // 格；0 = 全图
  affects: 'allyTower' | 'enemy';
}
```

**为什么必须改**：策划案 §4.2.3 的**法师爷爷**有 3 个光环效果（+15% 攻击 / +15% 攻速 / +10% 射程），§4.2.4 的**训导主任**有 2 个。单对象表达不了。

更危险的是：若 `aura` 与 `auras` 并存，**引擎读 `aura`、数据写 `auras`，效果会静默失效且没有任何报错**——这类"配置写了但没生效"的 bug 在塔防里极难被发现（玩家只会觉得"这塔怎么这么弱"）。

**约束**：`aura` 已从 Schema 中删除，`validate-data` 有硬门禁「`units` 弃用 `aura`，只允许 `auras[]`」。当前 5 个单位使用 `auras[]`。

## 13. SimEvent 与语义增补（v0.1.3）

> **背景**：`engine-dev` 在实现 M0 时发现 §6 的 `SimEvent` 联合类型**缺 3 类状态变化**，导致 UI 无法得知这些事件发生。以下是裁决后的增补。

### 13.1 `SimEvent` 补 3 项（`engine-dev` 提出，主策划裁决采纳）

```ts
// 追加到 §6 的 SimEvent 联合类型
| { type: 'undo';            towerId: number; refund: Fixed }   // 撤销建造（原复用 sell，语义混淆）
| { type: 'skillActivated';  skillId: 'salary' | 'bramble' | 'midas'; amount?: Fixed }
| { type: 'waveStats';       stats: WaveStats }                  // 上一波的结算（见 13.2）
```

并把 `gameOver` 的结果扩为三态：

```ts
| { type: 'gameOver'; result: 'win' | 'lose' | 'ascended'; wave: number }
```

**`'ascended'` 是主动蜕变的第三种结局**——策划案 §4.7.1 允许玩家在第 20 波后主动结束本局结算，它不是"输"。原定义只有 `win`/`lose`，UI 收到 `lose` 会显示失败界面，而玩家其实是主动离场。

### 13.2 `waveAcc` 的语义（澄清，非改动）

`engine-dev` 用测试钉住的语义：**`WorldSnapshot.currentWaveStats` 只代表「当前波」的累加值，波次结束即重置。** 「上一波统计」只存在于 `waveEnd` 事件里。

这是对的，但**快照读不到上一波数据**会让 UI 的"波次小结"必须在事件里缓存。因此 13.1 追加了 `waveStats` 事件（`engine-dev` 现用 `waveEnd.stats` 表达同一数据，二者语义等价，保留哪个由实现定，但**必须有一个能被 UI 直接消费**）。

### 13.3 `critRate` / `critMul` 的合成语义 —— **裁决：单位值覆盖全局默认**

契约 §3.3 同时定义了全局 `critRateBase`(50) / `critMulBase`(1500) 与单位表的 `critRate` / `critMul`，但**没说怎么合成**。`engine-dev` 选择了"单位值覆盖全局默认"，实现中一度写成 `critRateBase + def.critRate`（5%+5% = 10%），已修正为覆盖语义。

**裁决：采用「单位值覆盖全局默认」。** 理由：

```
窃金塔：critRate 50 (5%)，critMul 1500 (150%)   ← 与全局默认一致
非窃金塔：critRate 0，critMul 1000              ← 不暴击

科技线在其之上加成，并受全局上限约束：
  窃金暴击率   +5%/级 × 5 级 → 5% + 25% = 30% = critRateCap      ✓ 自洽
  窃金暴击效率 +25%/级 × 5 级 → 150% + 125% = 275% = critMulCap  ✓ 自洽
```

若改用"全局基础 + 单位加成"，小偷会变成 10% 暴击，且与 `critRateCap`(30%) 的关系失真。

**并且裁决：策划案 §4.1.2 的「暴击效率等级」= 窃金暴击效率科技线的等级（0–5），不是塔的 tier。**

`engine-dev` 在 M0 **拒绝**按 tier 放大暴击倍率——这个判断是对的：按 tier 放大等于凭空发明一个一阶强度来源，会让高 tier 塔获得未经设计的额外经济优势。

### 13.4 `attackInterval` 的 tick 量化（已知误差，数据侧须配合）

60Hz 定步长无法精确表示 1/1.2s：

```
1.2 次/秒 → 存 833 定点 → ceil 到 49 tick → 实际 1.2245 次/秒（快 2%）
误差上界：±1 tick（±1.7%）
```

**数据侧两条约束**：

1. **优先选用 1/60 秒的整数倍间隔**（即 `frequency` 的倒数 × 60 为整数）：如 1.0/s→60t、0.5/s→120t、2.0/s→30t、0.75/s→80t。
2. 无法整除时，`attackInterval` **宁可略大不要略小**（tick 换算向下取整会导致实际攻速偏快）。

### 13.5 BOSS 钱包系数 —— **不得为 1.0**

§4.5.2 的 4 个 BOSS 行「钱包系数」原写作「—」，`data-arch` 取 1.0。**这个取值有害**：实测 `w27`（飞升者波）每波总钱包只有 **3,663**，而相邻的 `w26 = 152,329`、`w28 = 334,085`——形成经济断崖，终局 BOSS 波变成"打完没钱"。

**裁决**：BOSS 必须有钱包系数，且**新增一条数据不变量**：

> **每个 BOSS 波的「每波总钱包」不得低于其前后相邻非 BOSS 波的 60%。**

起点值（待标定）：荒兽 ×12 / 心魔 ×12 / 转生者 ×16 / 飞升者 ×20。
注意**飞升者是 100% 窃金免疫**，它的钱包只能通过 `bountyRatio`（击杀奖励 17%）转化为收益——这正是策划案「BOSS 收益由波次结算奖励承担」的落点。

### 13.6 投射物池容量与「弹无虚发」是互斥的（记录，不阻塞）

`engine-dev` 发现的吞吐含义：`稳态并发 = 射速 × 飞行时间`。池容量 500 + "超出复用最旧"意味着

```
被丢弃比例 = 1 − 池容量 / (射速 × 飞行时间)
```

压力场景（35 塔 × 20 发/秒 = 700 发/秒、飞行 0.7s → 需要 490 并发，逼近 500 上限）实测只有 **7.5 次窃金/秒**落地（≈1% 的弹丸命中）。

**策划案自身配置不会触发**：1.5 发/秒 × 35 塔 = 52 发/秒 → 池驻留 9.6s ≫ 飞行时间，余量充足。故不影响 §8.5 的出货数值。

但**「500 并发」与「弹无虚发」在数学上互斥**，已在策划案 §8.5 补注，避免后续有人误以为池容量可以当"无限"用。

## 14. M2 裁决：经济可通关性（v0.1.4）

> **背景**：`balance-eng` 在批次 2 用真实数据跑通了 headless 模拟，发现 **数据层在数学上不可通关**。证据两条独立成立，已由主策划复现：
>
> 1. **解析上界**：`ttk-analysis.ts` 算「每波需求 DPS / 40 座最优塔的 DPS 上界」。N2 第 25 波起 > 1.0，第 30 波 **9.0×**；N5 第 30 波 **32.4×**。
> 2. **上界实验**（`tests/sim/upper-bound.spec.ts`）：**无限金钱 + 40 塔位全铺 T5 飞贼**，3 个种子全部 lost 在第 22 波（漏怪 30/339）；人口上限翻到 80（实测铺 61 座）仍 lost 在第 24 波。
>
> ⇒ 四种策略 × 五难度的 **0% 通关率是数据结论，不是 AI 结论**。

### 14.1 根因：缺少「金币 → DPS」的指数转换通道（一阶设计错误）

```
血量成长    1.283^29 = 1373×
收入成长    1.200^29 =  198×        （钱包曲线）
塔的强度成长   tier 仅 ~52×（T1→T5），而 §4.4.1 科技只有 +50%/+40%（线性！）

设计意图（策划案 §5.3）：
  "血量涨 1.283^n，收入涨 1.20^n，玩家把收入换成 DPS，所以净难度 = 1373/198 = 6.9×"
这个推理的隐含前提是「金币能线性转化为 DPS」—— 而它不成立：
  ① 塔位有人口上限（~40），建满即饱和
  ② tier 是一次性离散乘区，不是"每金币换多少 DPS"
⇒ 超出塔位/品阶容量的收入是**不可花费的**，转换不成 DPS
⇒ 198× 的收入成长大部分被浪费，1373× 的血量曲线无人能挡
```

**结论**：TD 游戏必须有**一条指数级的金币→DPS 通道**来吸收指数级的收入成长。策划案里唯一候选是科技树，而 §4.4.1 的科技是**线性**的（+10%/级 ×5 级 = 总共 +50%）。

这也解释了原作为什么反复强调「升级中华科技的花费绝对超过千万」——**科技树本来就是后期的唯一强度来源**，我把它写成了 +50% 的装饰品。

### 14.2 裁决：科技树从**线性**改为**乘法**

**这是结构性修复，不是数值微调。** 修改 §4.4.1：

| 科技线 | 原（线性） | **新（乘法）** | 5 级总效果 |
|---|---|---|---|
| 攻击强化 | +10%/级 | **×1.50/级** | **7.59×** |
| 攻速强化 | +8%/级 | **×1.40/级** | **5.38×** |
| 射程强化 | +6%/级 | ×1.10/级 | 1.61×（工具性，不参与 DPS 乘积） |
| 窃金效率 | +12%/级 | ×1.12/级（不变） | 1.76× |
| 窃金暴击率 | +5%/级 | 保持加法（有 30% 上限） | 5% → 30% |
| 窃金暴击效率 | +25%/级 | 保持加法（有 275% 上限） | 150% → 275% |

**验算**：`tier 52.5× × 攻击 7.59× × 攻速 5.38× = 2144×`，对血量 `1373×` 有 **1.56× 余量**；
换算到 `balance-eng` 的解析上界：第 30 波需求/上界从 **9.0× → 0.22×**（余量 4.5×，其中已考虑"解析上界假设 40 座全覆盖"的宽松性）。

### 14.13 裁决：BOSS 60% 不变量取「**较穷一侧**」

`data-arch` 实现了两种读法并把差异打印出来，等主策划裁决：

| 读法 | 要求 | 4 个 BOSS 系数需改为 |
|---|---|---|
| **取较穷一侧**（`min(前一个非BOSS波, 后一个非BOSS波)`） | ≥ 60% × 42,398 | **保持 ×12/×12/×16/×20** ✅ |
| 对两侧都成立 | ≥ 60% × w28 = 200,451 | ×30 / ×17 / ×17 / ×55 |

### 14.15 裁决：`blockExtraSteal` 采用**推导式增量**，且 **Q1 的判据改用真反事实**

`engine-dev` 实现的口径：`增量 = 该笔窃取 × slowWhileBlocked`（列阵减速强度）。实测 `1856 / 4640 = 40.0%`。

**这个推导是正确的**：列阵把移速乘 `(1−0.4)=0.6`，停留时间变为 `1/0.6 = 1.667×`，攻击次数同比放大。其中 `1.0×` 本来就有、`0.667×` 是额外增量，`0.667/1.667 = 40%` —— 恰好等于减速强度。所以「每笔窃取 × 减速强度」的累加等于总增量。✓

**裁决：接受该定义为契约口径**，但必须记录两条假设：

1. 它**只归因「列阵」减速**，不含**铁闸守卫的「锁链」拉回**（那同样延长停留时间）。⇒ 该指标对铁闸守卫**低估**。
2. 严格的反事实增量需要跑两个世界做差值，单遍模拟做不到。所以它是**诊断指标**，不是判据。

**据此追加裁决（重要）**：

> **Q1（军训系去留）的判据不得使用 `blockExtraSteal / stolenTotal`。**
> 判据必须改用 **`balanced` vs `noblock` 两个世界的对照**（通关波次差）—— **那才是真反事实**。
> `blockExtraSteal` 降级为诊断指标，仅用于解释"增量从哪来"。

理由：用一个**推导式归因**去裁决一个**系统存废**，是把近似当证据 —— 与本项目已犯过的"用错表当验证依据"同型。

### 15.1 裁决：心魔 `splitOnDeath` **只分一代**（归 `engine-dev`）

**这是当前唯一挡住通关的缺陷。** 证据链闭合：

```
含分裂    ：出怪 560 / 漏 46 / lost 第 25 波（第 1–24 波零漏怪）
关掉分裂  ：出怪 522 / 漏  0 / won 全部 30 波
```

`waves.json` 全 30 波共 **522** 只，含分裂时出怪 **560** ⇒ **分身又裂出了分身**。根因：`cleanupSystem` 里 `makeEnemy(w, e.defId, …)` 造的克隆 `defId` 与原体相同，`splitOnDeath` 仍为 2，**无递归深度保护**。

**裁决：分身带 `canSplit = false`（一代即止）。** 忠于 §4.5.2「死亡时分裂为 2 个半血分身」的字面。

**一个有助于判断严重性的技术细节**：半血分裂本身**总血量守恒**（1 只 → 2 只 × 50% = 100%）。所以伤害**不在血量，在数量** —— 数量指数增长 ⇒ 到达宝库的身体数指数增长 ⇒ **每个漏过去扣 1 命**。**它打破的是生命经济，不是血量平衡。** 故修法必须是"分身不再分裂"，**不是"调低分身血量"**（后者会顺手破坏总量守恒）。

**并追加一条缺失的门禁**：断言「某波出怪总数 == `waves.json` 该波配置总数」。出怪数被悄悄放大 7% 而没有任何检查发现 —— 这是铁律 8 的第四例。

### 18.4 ★ 新增判据：**静态总量闭环 ≠ 时序闭环**


### 19.2 ★★ 核心发现：窃金覆盖率实测 **16%**，而设计假设 **65–80%**

`balance-eng` 逐决策点采样（每一步都有数字）：

```
t0    w1  prep   金=3000 塔=0  科技=0 → [salary, build pickpocket]
t6000 w3  combat 金=119  塔=8  科技=0 → []
t9000 w5  prep   金=68   塔=10 科技=0 → []
t24000 w11 combat 金=211 塔=19 科技=0 → []
t36000 w15 combat 金=942  塔=22 科技=0 → []
```

**因果链**：可用金币长期低于 1,000 → 下一件是 800 金升级 / 1,300–1,500 金第一级科技 → **永远攒不到 → 0 科技**。根因不在策略清单，在**覆盖率 16%**。

**算术自洽**（不是 bug，是模型结果）：`2 路 × 3 塔 × ~2 次命中 × 4.6–15 金/击 = 每敌 30–90 金`；第 10 波单体钱包 ≈231 → **13–39%**，实测 16% 落在区间内。

**⇒ 整个经济校准（§5.2 / §5.5 / 科技总额 / 造价曲线）建立在一个达不到的前提上：实际收入只有设计的约 1/4。**

这与 `engine-dev` 早先的发现是同一件事：**神偷射程 2 格 + 1.5 次/秒 → 敌人走一趟只够打约 3 次**。

### 19.3 裁决：问题在 **★停顿点太弱**，而非 AI 战术 —— 先激活已设计好的机制

策划案 §4.6 把★停顿点写成「**本项目对原作最重要的致敬**」—— 原作高手攻略的核心理念是「**怪会在一个地方稍微停顿一下，那个位置恰好可以打到那里**」：玩家把窃金塔**集中**在停顿点，而不是均匀铺满路径。

**但 `haltPointStopDuration = 0.6s` 让这个机制形同不存在**：`0.6s × 1.5 次/秒 = 多打不到 1 次`。

**算一下 2.5s 停顿**：在停顿点周围堆 4 座窃金塔（射程 2 格），每座在停顿期得 `2.5s + 自身覆盖窗 ~2s = 4.5s` → 每座 ~6.75 次命中 → 4 座共 **27 次** ≈ 135 金 / 231 钱包 = **58% 覆盖率，只用 4 座塔**。

对比现状（均匀铺 3 座）→ 16%。**同样塔数，集中 vs 均匀差 3.6 倍。**

⇒ **不是"AI 不会玩"，是"设计的核心机制被参数关掉了"。** 主策划把★停顿点写成"最重要的致敬"，却给了它一个可忽略的数值。

**裁决：先扫描 `haltPointStopDuration`，在内存里做，不改数据。**

| 项 | 内容 |
|---|---|
| 扫描值 | `0.6（现状）/ 1.0 / 1.5 / 2.0 / 2.5 / 3.0` |
| 必测三指标 | ① **窃金覆盖率**（目标 65–80%）② **单波时长**（2.5s × 30 只 = 额外 75s，停顿变长的代价）③ 24 格通关率 / balanced 均到波 |
| **必测两摆位对照** | **均匀铺**（现状沿路径摊开）vs **集中堆**（塔向★停顿点聚集） |
| 执行者 | `balance-eng`（内存注入，**不改 `src/data`**）；确定值后由 `data-arch` 落地 |

**预期**：集中堆在长停顿下显著优于均匀铺 ⇒ 机制被激活，**且同时强化 Q1**（军训系在停顿点阻挡 → 停留更久 → 偷得更多），Q1 可能从"无价值"变成"核心玩法"。

### 19.4 裁决：第二、三级旋钮的**顺序不得颠倒**

| 级 | 旋钮 | 性质 |
|---|---|---|
| 1 | `haltPointStopDuration` 扫描 | **让已设计好的机制生效** |
| 2 | 神偷系射程 `2.0 → 2.5 格` | **让设计生效**（同上） |
| 3 | 承认 65–80% 覆盖率不可达 → **下调目标 + 按比例重新标定钱包曲线** | **改设计假设**（大改，需另开裁决） |

**一次只动一个，且不得把第 3 级提前。** 前两级是"让设计生效"，第 3 级是"改设计假设"—— 顺序反了就等于用改假设去掩盖实现失败。

### 19.5 裁决：适配层门禁采用**变异覆盖**法，上限一轮

`balance-eng` 问"字段级映射门禁"的工作量上限。

**裁决：一轮；若超出就停下报进展。**

**方法（比"检查字段是否被读过"更可执行）**：

```
对 src/data 的每张表、每个必填字段：
  把该字段变异成一个哨兵值 → 断言 SimContent 因此发生变化
  若变异后什么都没变 ⇒ 该字段没被消费 ⇒ 报红
```

**这正是铁律 8 的形式**：一条冗余字段的变异就是一次"空测量"，而变异覆盖能直接抓到它。

范围限定 `src/sim` 实际消费的表（units / enemies / waves / tech / difficulty / constants / map）；`audio` / `relics` / `equipment` 本期不接模拟层，排除并注明。

## 20. M2 第七轮：主策划的覆盖率假设被实测推翻

### 20.1 ⚠️ 第二次「用推算代替测量」

§19.3 主策划预测「2.5s 停顿 + 停顿点周围 4 座窃金塔 = **58% 覆盖率**」。`balance-eng` 扫完实测：

| | 主策划预测 | 实测 |
|---|---|---|
| 2.5s 停顿 + 集中摆位 | **58%** | **31.9%** |
| 停顿时长 0.6s → 3.0s（5×） | 大幅提升 | **+5.1pt**（28.3% → 33.4%）|
| 摆位 均匀 → 集中 | 3.6× | **+8~14pt** |

**两次连续**：§19.5 之前预测「2.5s × 30 只 = 额外 75s/波」（被仪器自检 2 推翻），§19.3 预测 58% 覆盖率（被扫描表推翻）。

**根因（`balance-eng` 给的机理，主策划采纳）**：

```
覆盖率 ≈ (射程内塔数) × (每塔命中次数) × (每次命中的窃金量)
停顿时长放大第二项；射程放大第一项。而射程仅 2.0 格 ⇒ 第一项极小
⇒ 在同一位置加时长，是最贵的做法
```

主策划的算术错在**假设"停顿点周围有 4 座塔在射程内"** —— 射程 2.0 格时实际射程内塔数远少于此（实测 clustered 塔到停顿点平均 **2.06 格**，uniform **4.82 格**）。

> **规律（第 7 次）**：主策划连续两次对**具体数值**下预测，连续两次被实测推翻。
> **裁决：主策划不再对具体数值下预测。** 只定「测哪几个维度」与「达到什么算过」。
> 这是本项目主策划错误清单里第 7 条，也是唯一一条能通过**改变自己的行为**消除的（前 6 条靠"去查原始层"，这条靠"不下数值预测"）。

### 20.2 ★ 关键：三乘区里**漏测了第三项**（可能是主导项）

| 乘区 | 状态 | 结论 |
|---|---|---|
| 射程内塔数 | 摆位已测（+8~14pt）；**射程本身未测** | 有影响，但补不上 16%→65% |
| 每塔命中次数 | 停顿时长已测（+5.1pt） | **弱，已关闭** |
| **每次命中的窃金量** | **完全未测** | ↓ 按 `stealAmountCore` 计算可能是主导 |

```
stealAmountCore = StealBase × LevelMul × (1 + 0.02 × attack)
T1 小偷 ：  4 × 1.00 × 1.16  =     4.64 金/次
T3 神偷 ： 14 × 1.85 × 1.90  =    49.0  金/次   ← 10.6×
T5 飞贼 ： 55 × 3.80 × 6.60  = 1,379    金/次   ← 297×
再叠窃金效率满级 ×1.76 → T5 ≈ 2,427 金/次
```

**⇒ 单次窃金量在 T1→T3 之间就有 10.6 倍差距，远大于摆位的 8~14pt 与停顿的 5pt。**

而 `balance-eng` 的 AI 采样显示它**长期只有 3 座窃金塔**、覆盖率恒 16% —— **若把 T1 升到 T3，同样塔数、同样摆位，窃金量该差 10 倍。**

### 20.3 裁决：下一轮测**三个维度**，其中 AI 侧维度优先

```
维度 A（AI 侧，优先，不需改数据）：
  A1 建造优先（现状）—— 有钱就铺新塔
  A2 升级优先        —— 先把手上的窃金塔升到 T3+ 再铺新的
维度 B（数据侧）：神偷射程 { 2000, 2500 }
维度 C（摆位）  ：{ uniform, clustered }
```

**要求**：**先单独测 A1 vs A2**（B/C 固定现状）。**若升级倾向是主导因素，则不需要动任何数据**，前面三轮关于射程/停顿/摆位的讨论都是次要的。

然后测 `A2 × B × C`（8 格，每格 2 局，N2 为主）。

**每一格必须同时报「覆盖率 + 平均窃金塔等级 + 窃金塔数量」** —— 否则无法分辨是"塔多"还是"塔强"在起作用。**这正是主策划 §19.3 错误的根源：假设了塔数与射程，没看实际值。**

### 20.4 裁决：第 3 级旋钮的**门槛与方案**提前写明

若 **A2（升级优先）** 仍拉不到 65%，则**直接进第 3 级，不再折腾射程** —— 那时已证明"同一几何下把塔做强也不够"，问题在**目标本身与钱包曲线的匹配**。

**第 3 级方案（预先裁定，免得届时再讨论）**：

> **保持 65–80% 覆盖率目标不变**，按实测可达覆盖率**反推并下调钱包曲线**（`walletIndex` 或 `baseWallet`）。
>
> 理由：覆盖率是**玩家的体验指标**（"我偷到了大部分钱"），钱包曲线是**内部标定参数**。**改内部参数去适配体验目标，比改体验目标去适配参数更对。**

### 20.5 新增纪律：「**不报平线**」（与铁律 8 方向相反的同类问题）

`balance-eng` 的仪器自检 2 发现自己被要求测的「单波时长」指标**不敏感**：

```
末 8 波 waveEnd tick（0.6s vs 3.0s）：7 波逐位相同，末波反而【早 6 tick】
原因：资源上界阵容在停顿期间就把敌人打死了 —— 停顿不推迟波次结束
⇒ 该指标在这套阵容上不会发生；弱阵容又活不到第 25 波
```

它选择**如实报为缺口，而不是报一条平线**，并提出这条纪律。**主策划采纳并升级为通用要求。**

**至此"不可解读的结果"有四种形态**：

| 形态 | 例子 | 防守手段 |
|---|---|---|
| ① 门禁**没运行** | M0 的 `pnpm lint` 对 `.ts` 是空操作 | 让门禁真的跑起来 |
| ② 门禁在跑但**没测对象** | `validate-data` 无人检查可通关性 | 铁律 8 第 1/2 条（负对照 + 窄作用域）|
| ③ 输入**陈旧** | 跨 agent 并行编辑时读到中间态 | 结论必须附被依赖文件的 mtime（§19.6）|
| ④ 指标**不敏感**（报平线） | 「单波时长」对停顿代价恒不变 | **先做仪器自检，再给表**（§20.5）|

**并要求：凡是要报一张数据表的，先把"这张表的指标是敏感的吗"证明出来** —— `balance-eng` 的 `halt-instrument-check.ts` + 4 条机制回归用例是标准做法（**把自检做成可执行交付物**，而不是一次性检查）。

### 20.6 裁决：变异覆盖门禁**批准**，按 `balance-eng` 的设计，一轮

其设计包含**负对照**（变异明确**不该**被映射的字段 `units[].description` / `sprite` / `icon` → 断言 `SimContent` **不变**）——

> **这正是铁律 8 要求的"证明探针不是恒真的"。** 没有它，一个"变异什么都变了"的探针会全绿而毫无意义。

范围：`units / enemies / waves / tech / difficulty / constants / map` 七张；排除并注明 `audio / relics / equipment`（本期不接模拟层）。

**排序：排在 §20.3 之后** —— 覆盖率是当前唯一主线。若时间不够，先交 `A1 vs A2` 对照，门禁下轮。

## 21. M2 第八轮：A 维度是最大杠杆、以及第 3 级方案被反例推翻

### 21.1 ⚠️ `balance-eng` 自查出**自己**的覆盖率指标 bug（且它污染了主策划的判断依据）

跑扫描时覆盖率算出 **104% / 151%** —— **在定义上不可能**（窃金 ≤ 钱包）。

```
根因：分子 stolenTotal 含【进行中的那一波】，分母 Σ(waves[].walletTotal) 只含【已结束的波】
     ⇒ 死在第 N 波中途时，分母少一整波 → 覆盖率虚高
实测：noop@N2 = 1042‰ → 修正 741‰ ｜ balanced@N4 = 1455‰ → 修正 606‰
```

**它主动指出这对主策划的影响**：

> 你判断"覆盖率上不去"时看到的 `noop = 89–104%` 这条反证也是假的。修正后 `noop@N2 = 74.1%`。

**⇒ 主策划据以判断"覆盖率上不去"的整张表都被污染过。** 修正后 N2 = **15.6%**（方向未变，幅度失真）。

**裁决：加一条定义性硬断言 `stolenTotal ≤ walletTotal`（覆盖率 ≤ 1000‰），越界即报红。**

理由：这是一个**极便宜的探测器** —— 任何"分子含进行中、分母不含"这类口径错配都会立刻撞上它。**铁律 8 的另一种形式：一个不能被违反的定义性边界，就是最便宜的负对照。**

### 21.2 裁决：**A 维度（经济倾向）是最大杠杆，且零数据改动**

```
build-first   2.0 uniform N2：覆盖率 15.7%  8 塔  平均 T1.12  最高 T2  每塔 335
upgrade-first 2.0 uniform N2：覆盖率 26.2%  8 塔  平均 T1.19  最高 T2  每塔 418   ← +10.5pt
```

| 维度 | 杠杆幅度 | 结论 |
|---|---|---|
| **A 经济倾向（升级优先）** | **+10.5pt** | **最大单因子，不需要改任何数据** |
| C 摆位（clustered） | +4.1pt | 有效但次要 |
| B 射程 2.0→2.5 | **+0.5pt**（uniform）/ +4.4pt（clustered） | **弱杠杆，与第 1 级停顿时长同量级** |

> **⚠️ 射程也是弱杠杆。** §20.3 主策划建议「跳到第 2 级（射程）」—— **那会是又一次死胡同**（幸好未无条件批准）。
>
> **第 1、2 级旋钮（停顿时长、射程）至此均为弱杠杆，已关闭。**

### 21.3 ★ 关键发现：主乘区**从未被打开**

**每一格的最大窃金塔等级都是 T2** —— AI **从未升到 T3**（`master_thief` 2,500 金）。

所以「**每次命中的窃金量**」这个乘区（§20.2 算出 T1→T3 有 **10.6 倍**）**一次都没有被真正打开**。`upgrade-first` 只是在便宜档位内重排清单。

**⇒ 前面三轮关于「射程 / 停顿 / 摆位」的讨论，全都是在没打开主乘区的情况下调次要乘区。** 这是本项目到目前为止**方法论上最重要的一次自我纠正**。

### 21.4 裁决：第 3 级（下调钱包曲线）**暂停**，并给出严格重新进入条件

`balance-eng` 用反例推翻主策划第 3 级方案的前提：

```
修正后覆盖率：
  noop     （纯小偷）  N1 576‰  N2 741‰  N3 827‰  N4 631‰  N5 666‰
  balanced （40/20/40）N1 120‰  N2 156‰  N3 377‰  N4 606‰  N5 690‰
```

**同样的数据、地图、停顿时长与射程 —— `noop` 在 N2/N3 落在 65–80% 带内** ⇒ **覆盖率目标本身可达，差的是分配**（`balanced` 把钱花在不产钱的输出塔上，把 74% 稀释到 16%）。⇒ **下调钱包曲线会去修一个没坏的东西。**

**主策划裁决：反例成立，前提被推翻。但用 `balance-eng` 自己标注的弱点来定边界**：

| 数据点 | 观察窗 | 可比值 |
|---|---|---|
| `noop@N2 = 74.1%` | **6 波**（第 6 波死） | ❌ 与 full-run 不可比 |
| `balanced@N4/@N5` | **1–2 波** | ❌ 已标为假象 |
| `balanced@N2 = 15.6%` | **12 波** | ⚠️ 分配被稀释 |

**⇒ 目前没有任何一条是"完整 30 波、分配健康"的覆盖率读数。** 在这种状态下改钱包曲线，是拿 6 波窗口的数字去动全局标定。

**裁决：第 3 级暂停（不撤销）。重新进入的唯一条件**：

> **一次完整 30 波的运行（分配健康、能活到第 30 波）测出覆盖率 < 65%。**
> 若那种运行下覆盖率 ≥ 65%，**第 3 级永久撤销**。

### 21.5 裁决：主线是「**覆盖率 × 存活**」的缺口驱动分配

`balance-eng` 把它精确定名：`noop` 拿得到覆盖率但活不下来（杀不了怪 → 漏光）；`balanced` 活得久但覆盖率被稀释。**要解的是「同时」拿到两者。**

**作为唯一主线**：

```
缺口驱动分配（每波决策前算两个缺口）：
  覆盖率缺口 = 目标 65–80% − 当前覆盖率   → 低于目标：优先买/升窃金塔
  生存缺口   = 需求 DPS − 当前 DPS         → 有缺口：优先买输出
  两个都缺时按【缺口相对比例】分配，而不是固定 40/20/40
```

**要求**：每波把两个缺口值与最终决策打出来（至少前 20 波）。否则无法判断它是"按缺口买"还是"碰巧买对"。

### 21.6 裁决：A 维度的"真实测试"—— **只改策略，不动数据**

`balance-eng` 问边界。**主策划裁决：先只改策略。**

可达性算术（主策划核算）：第 10 波累计钱包 2,510（N2），65–80% 覆盖率 → ~1,800 金；加起始 2,000 → **约 3,800 金可用**；`T3 = 2,500 金` ⇒ **买得起**（前提是没把钱全铺成 T1 塔）。

**⇒ 这是分配问题，不是定价问题。**

- **允许 AI 为升级攒更久的钱**（批准）
- 让升级优先级**跨过 2,500 金这个槛**（现在的 `upgrade-first` 只在便宜档位内重排）
- **不动 `master_thief` 造价**（`data-arch` 领域）

**预先授权**：若"显式攒钱买 T3"的策略跑完仍拿不到 T3，**那才构成数据信号**，届时另开裁决考虑调造价或 T1/T2 性价比曲线。**策略没试够之前不动数据。**

**并要求「最高窃金塔等级」为一等指标** —— §21.3 的发现正来自它。

### 21.7 陈旧输入的**第二个来源**：自己少跑一步

`balance-eng` 自 catch：

> `balance` 与 `balance-report` 是两步，我只重跑了前者就读了旧的 `report.csv`，看到的是修 bug **之前**的数字。

这与 §19.6 是**同一形态（③ 输入陈旧）的不同来源**：一个是**别人在改**，一个是**自己少跑了一步**。

**裁决：凡两步以上流水线，报告结论必须来自端到端重跑**；或至少核对产物 mtime ≥ 输入 mtime。

## 22. M2 第九轮：缺口驱动建成、以及"可审计"要求立刻回本

### 22.1 结果：覆盖率 ↑2.9×，存活 ↓2.4×，目标未达成

| `noop` | 74.1% | 6 | 6.0 | T1.66 | T2 | 60.0% |

### 22.2 ★★ 根因：`balance-eng` 的估计器犯了**与分析上界同一个错**

```
它的 dpsNeed =（需求DPS − 当前DPS）/ 需求DPS
需求 DPS 取自 ttk-analysis 的 totalHp / 波时长
⇒ 假设了【100% 命中覆盖 + 全程开火】
而真实存活需要的是【峰值能顶住】+【射程真覆盖】
```

**证据在逐波 trace 里**：第 5 波 `dpsNeed = 3.4%`（AI 认为生存安全），**实测漏怪率 75%**。
⇒ 估计器让 AI 在**看着安全**的时候持续买经济，把 DPS 饿死。

**它自己的定性（主策划完全同意）**：

> 缺口驱动的失败**不是"缺口驱动"这个方向错，是我那把尺子错了** —— 与分析上界同一个乐观假设的错。

> **这是本项目第三次有人认出「理想化模型冒充实际行为」这个病**：
> ① `engine-dev` 的像素校验负对照（LINEAR 组证明混色检测器非空）
> ② 主策划要求把"上界实验"改名为「资源上界 / 启发式摆位 → **非行为上界**」
> ③ `balance-eng` 自己的 `dpsNeed` 估计器
> **第三次是它自己认出来的，而且是在没有外部提示的情况下。**

### 22.3 ★ 「可审计」要求立刻回本 —— 它产出了本轮唯一的根因

§21.5 主策划要求「**每波把两个缺口值与最终决策打出来**（至少前 20 波）」，理由是"否则无法判断它是按缺口买还是碰巧买对"。

**那条要求直接产出了本轮唯一的根因**：没有那条 trace，`dpsNeed = 3.4% vs 漏怪 75%` 这个矛盾会一直藏着 —— 而表面上覆盖率从 15.6% 涨到 44.9%，**看起来在稳步进步**。

> **通用规则（新增）**：**决策必须可审计。** 让策略把它每一步的判断依据与实际选择打出来 ——
> 审计的成本很低，而**它能抓到的东西（错误的度量）用其他方式几乎抓不到**：
> 一个错的度量不会让程序崩溃、不会让断言变红，它只会让 AI 稳定地做错事。

### 22.4 裁决：批准修生存缺口估计器 —— 但标定方法**收紧**

`balance-eng` 的方案：用 `balanced` 逐波数据反推"开始漏怪时的 DPS / 当时塔数"当门槛。

**方向对，但"只从一条策略的 trace 反推"是同一个错误的缩小版** —— `balanced` 的漏怪点本身是它分配方式的产物。

**收紧为**：

```
从 balanced / upgrade-first / noop / gap 四条 trace 各取「首个漏怪率 > 0 的波」
对每条算：该波（当前DPS / 需求DPS）→ 四个比值
门槛取【最保守的那个】，并【报告极差】
```

- 四条比值**接近** ⇒ 门槛稳健，直接采用
- **离散很大** ⇒ 说明漏怪不只由 DPS 决定（还有射程覆盖、摆位、护甲类型）⇒ 门槛写成**两个条件**（DPS 比 + 覆盖比），而不是一个数

**并且门槛必须写成可执行断言**（漏怪率 > 0 时，该波 DPS 比必须低于门槛）—— 否则它又是一个"只在报告里存在的校准值"。

### 22.5 裁决：优先级按 `balance-eng` 提的顺序 —— **门禁第一**，上限一轮

**理由（不是盖章）**：

1. **它是有限的、机械的**（其自估"正好一轮"）。**欠了三轮的东西通常是"看起来不急、实际一直被挤掉"** —— 再挤一次就等于告诉它"永远可以等"。
2. **适配层已经三次成为瓶颈**（漏整张 `tech` 表 → 漏 `target` → `map.json` 未迁）。它在**所有东西的关键路径上**，门禁是防第四次的唯一手段。
3. **接下来的工作会往上加新度量**（生存门槛、覆盖比…）。**在适配层还没有自检时加新字段，就是在同一位置第四次冒险。**

**上限一轮。若超出，停下报进展；不得为做完而降低断言质量** —— 尤其那条负对照（变异一个**不该被映射**的字段必须断言 `SimContent` **不变**）。**没有它，一个"变异什么都变了"的探针会全绿而毫无意义。**

### 22.6 裁决：T3 的"数据信号"条件—— **未达成**，接受 `balance-eng` 的判断

主策划预设的判据是「显式攒钱买 T3 仍拿不到 T3 ⇒ 数据信号」。`balance-eng` 拒绝触发它：

> 我不认为现在够格下这个结论 —— 因为 AI 同时还在饿死 DPS，它死得太早（第 5 波），**根本没走到"钱够不够"那一步**。

**裁决：条件未达成。重估时机 = 生存估计器修好、AI 能活到第 10+ 波之后。在此之前不动 `master_thief` 造价，也不再讨论这条。**

> **这是它连续第二轮拒绝用一个"形式上满足、实质上无意义"的结果去支持一个改动**（上一轮是拒绝用 6 波窗口的 `noop@74%` 支持撤销第 3 级）。
> **这类拒绝比任何一次"达标"都更能提高整个项目的信噪比。**

### 22.7 裁决：统一「最高窃金塔等级」的单一来源

它自报 `gap.maxThiefTier()` 是**死接口**（返回 0），报告里的 T2 来自 `run.ts` 统计。

**裁决：批准清理，并把该指标统一到 `run.ts` 一处。** 两个来源报同一个指标，**迟早会有一个是错的，而错的通常不会被发现**。

### 22.8 第 3 级条件**不变**，并记一个注意点

> 重新进入的唯一条件：**一次完整 30 波（分配健康、活到第 30 波）的覆盖率读数 < 65%。**

**注意本轮**：`gap@N2 = 44.9%` 只活到第 **5** 波 —— **窗口比 `balanced@N2` 的 12 波更短**。所以这个数**不能**用来支持任何关于"覆盖率是否可达"的结论。`balance-eng` 也没有这么用。

**"目前仍没有任何 full-run 可比读数"这句话，从 §21.4 延续至今，一个字都不用改。**

> 理由：**本项目所有重大事故都不是"门禁报错了"，而是"门禁在它看不见的地方放过了"。**
> 知道一条门禁的边界在哪，与知道它通过同样重要。

## 24. M2 第十一轮：预测量不可用 ⇒ 主线改为**反馈式**

### 24.1 门槛标定结论：单条件不够，且主策划提的"覆盖比"**被数据否掉**

```
n=12 ｜ 最小 90.3% ｜ 最大 196.7% ｜ 极差 106.4pt
```

| 策略 | 首个漏怪波 | 该波 DPS 比 | 该波覆盖率 |
|---|---|---|---|
| `balanced`(build-first) | 9 / 10 / 10 | 90.3% / 90.3% / 109.7% | 13.9–16.4% |
| `balanced`(upgrade-first) | 6 / 6 / 6 | 196.7% ×3 | 46.8–47.4% |
| `noop` | 3 / 3 / 3 | 151.8% ×3 | 90.7–91.5% |
| `gap` | 2 / 2 / 2 | 103.0% ×3 | 65.7% |

按 §24 预先定的规则（离散大 ⇒ 不取平均），`balance-eng` **没有取平均、没有挑好看的值**。

**★ 分裂方向比门槛本身有用**：

```
noop     覆盖率 90.7%（最高）→ 却在比值 151.8% 才首次漏怪
balanced 覆盖率 13.9%（最低）→ 在比值 90.3%（最低）就漏了
⇒ 覆盖率与漏怪比值是【正相关】，不是"覆盖率低所以漏"
```

**真正的缺失项是「命中率 / uptime」（由射程决定）**：`effectiveDps` 假设每塔 100% 开火且必中 —— `noop` 只有射程 2.0 的神偷，该假设把它**高估得最多**，所以它撑到 152% 才漏；`balanced` 有射程 5.2–6.5 的弓塔，uptime ≈ 1，比值近乎如实。

⇒ **主策划在 §22.4 提的"覆盖比作为第二条件"被数据否掉。** 已接受。

### 24.2 ★★ 新增第五种「不可解读的结果」形态：**被测量对采样约定不稳定**

```
标定脚本：noop 首个漏怪 = w3 / 151.8%
断言测试：noop 首个漏怪 = w2 / 222.6%     ← 同策略、同数据
差异来源：两次采样的"该波 DPS"取自不同时刻（波切换 vs waveEnd 各记一次）
```

**`balance-eng` 的定性（主策划采纳）**：

> 这不只是"门槛取不准"，而是**被测量的量本身对采样约定不稳定**。把这种量写成硬断言，等于把我恰好这么采样固化成一个门禁 —— **那是空测量的另一种形态**。

**它的处理全对**（主策划确认）：**没有**把上界放宽到 250% 让它变绿；降级为**记录器**并显式声明不承担判定职责；只保留负对照（证明判定逻辑本身可分）；把"为什么不能当门槛"连同两组数字写进文件头。

**五种「不可解读」形态至此齐全**：

| 形态 | 例子 | 防守手段 |
|---|---|---|
| ① 门禁**没运行** | M0 `lint` 对 `.ts` 空操作 | 让它真跑 |
| ② 门禁在跑但**没测对象** | 没人检查可通关性；护甲通道贡献 0 像素 | 铁律 8（负对照 + 窄作用域）|
| ③ 输入**陈旧** | 跨 agent 中间态；两步流水线少跑一步 | 结论附 mtime；端到端重跑 |
| ④ 指标**不敏感** | 「单波时长」对停顿恒不变 → 报平线 | 先做仪器自检，再给表 |
| ⑤ **被测量对采样约定不稳定** | 同策略同数据：151.8% vs 222.6%（差 47%） | **把量钉死成一个具名、单点的读取函数** |

> **⑤ 的特殊性**：前四种都能靠"加一条断言或配对对照"防；**⑤ 只能靠"把量的定义钉死"来防** —— 因为问题不在断言，在**量本身没有单一定义**。

### 24.3 ★ 裁决：主线改为**反馈式**（主方案，不是兜底）

`balance-eng` 提出"用**上波实测漏怪**驱动，不预测，代价是慢一波"。

**主策划裁决：采纳，并且不再先试"射程覆盖比"。**

1. **预测模型连败两次**（`dpsNeed` 估计器 → 本轮 `DPS 比` 门槛）。第三次的期望收益在下降，而每次失败要花一整轮。
2. **反馈在构造上就是稳的** —— 用实测结果，不需要模型。而我们已经证明「漏怪不能被任何**可算**的阵容指标稳定预测」（极差 106.4pt + 采样约定差 47%）。
3. **代价可接受**：一波延迟（单波 35–50s，全局 30 波）。**而且真人玩家就是这么玩的：看到漏怪才反应。** ⇒ 让 AI 用真人的策略，**更贴近"参考玩家"这个定位**。

**⇒ `gap` 的两个维度都改成反馈式**：

| 维度 | 信号源 |
|---|---|
| **生存** | **上一波实测漏怪数**（漏了就转输出） |
| **经济** | **覆盖率**（本身就是实测值，天然是反馈） |
| **买什么类型** | **波次预告**（`hint.recommendArmor/recommendAttack` + 敌人构成） |

**分工理由**：**预告给的是定性信息**（"这波是城甲"），**不需要模型**；**定量判断**（"要多少 DPS"）我们已证明算不准 —— **那就别算**。

### 24.4 裁决：采样约定**统一**，并加防 ⑤ 的负对照

**统一到「波结束时的 DPS」**，做成**唯一具名的读取函数**（如 `dpsAtWaveEnd(w)`）；所有消费方只能用这个函数，**禁止各自在波切换 / `waveEnd` 处取值**。

**并要求一条断言**：同一 `(seed, 难度, 策略)` 下，**用两条不同路径读出的该值必须相等** —— 这是防形态 ⑤ 的负对照。

### 24.5 裁决：③ 键清单与反馈式重写**同轮**，上限仍一轮

反馈式方案**可能不需要新常量**（用实测值而非阈值），盲区压力下降；**但 ③ 仍要做**，且与反馈式重写同轮（两者都是结构性改动，一起做省一次上下文切换）。

**若塞不下**：先交反馈式重写（主线），③ 明确报未完成。

### 24.6 主策划第 8 次判断错误 + 新增自限规则

§22.4 主策划提的"覆盖比作为第二条件"**被数据否掉**。

**这是主策划在该项目第 8 次判断出错，也是连续第 4 次被 `balance-eng` 推翻**：
> ① 58% 覆盖率预测 ② 射程是主杠杆 ③ 需要下调钱包曲线 ④ 覆盖比是第二条件

**规律**：主策划对**机制层面**的判断（问题属于哪一类、该查哪个维度）越来越准；对**"具体是哪个量"**的判断连续出错。

**新增自限规则（与 §20.1 并列）**：

> **主策划不再指定"用哪个量"做判据** —— 只指定「要达到什么」与「不允许怎么作弊」。
> **选择哪个量需要反复实测，那属于执行方。**

## 25. M2 第十二轮：反馈式建成但**闩锁**、以及三条路径全部撞墙

### 25.1 反馈式结果：存活修好了，覆盖率反而掉了

| 策略 | 窃金覆盖 | 均到波 | 窃金塔数 | 平均等级 | 漏怪率 |
|---|---|---|---|---|---|
| **`gap`（反馈）** | **9.8%** | **12** | 2.0 | T1.50 | 23.2% |
| `balanced` | 15.6% | 12 | 8.0 | T1.12 | 23.2% |
| `noop` | 74.1% | 6 | 6.0 | T1.66 | 60.0% |

**存活从预测式的第 5 波提到第 12 波（与 `balanced` 打平）；但覆盖率从 15.6% 掉到 9.8%。**

⇒ **`gap` 目前被 `balanced` 严格支配**（存活相同、覆盖率更低）。**目标未达成 → 第 3 级维持暂停。**

### 25.2 ★ 结构性缺陷：纯反馈**闩锁**在最后一个信号上

`balance-eng` 自己命名：

> 第 8 波起**每一波都漏怪** → 反馈永远指向"补输出" → 经济被永久饿死（只有 2 座窃金塔）。**纯反馈会锁死在最后一个信号上。**

**这是控制论里的经典问题**：纯比例控制器**没有积分项**，会闩锁在最后一个信号上，或振荡。

### 25.3 ★ 「可审计」要求**第二次**抓到真缺陷

```
第一版在"补输出"分支买了 worker（第 3/8/9 波）
—— 而 worker.attack = 0（产木单位）
⇒ 在漏怪时买它 = 花光现金换零 DPS
已修：生存分支过滤所有 attack ≤ 0 的动作；买不起则攒钱（什么都不做）
```

| 次 | trace 抓到的 | 性质 |
|---|---|---|
| 第 1 次 | `dpsNeed = 3.4%` 而实测漏怪 75% | **度量错** |
| 第 2 次 | 漏怪时买 `worker`（attack=0） | **逻辑错** |

> **通用结论（再次确认）**：**让决策可审计，审计就会找到度量与逻辑的错。** 两次都是它自己在写 trace 时发现的，没有外部提示。

### 25.4 采样约定统一 —— 负对照选得准

`src/balance/measure.ts` 的 **`dpsAtWaveEnd(w)`** 是唯一具名读数，定义钉死为 `Σ attack_eff / interval_eff`，**不加克制矩阵**（那是"对某一波"的属性，会把阵容强度与波次护甲混在一起），**在 `waveEnd` 被 drain 的那一刻读取**。

```
[采样唯一性] balanced / gap：11 个波末读数，两条独立路径不一致 = 0
[★ 负对照] waveEnd 时刻 DPS=67.054 ｜ 1 tick 后 =75.054
```

**负对照选得准**：换 1 tick（AI 在备战期建了一座塔）值就变 ⇒ **证明这个读数的时刻是"承重"的** ⇒ 从而证明"把它钉死"有价值。**一个不承重的约定不需要钉死。**

### 25.5 裁决：用**记忆（aging）**解闩锁，而非配额

`balance-eng` 的候选：① 预算配额（每 N 波至少 1 波投经济）② 双信号加权/轮换 ③ 回到预测（它不建议）。

**裁决：② 为主。① 是 ② 的粗糙特例** —— 它会在经济已经够的时候白白浪费。

**原理**：闩锁的根因是控制器**没有记忆**。经典修法是加**积分/老化项** —— 追踪每个缺口**已被连续忽略几波**，让积累更久的最终获胜。

**但主策划不指定具体形式**（§24.6 自限规则）。只定三条边界：

1. **不得引入新的、未经验证的度量** —— 在这上面已连败两次。只用**已有两个反馈信号**（漏怪数、覆盖率）+ 一个**计数**（连续未满足波数）。
2. **aging 常数必须由扫描确定，不许猜**：扫 `{1,2,3,4,5}` 波，**覆盖率与存活两个指标都报**。
3. **必须可解释**：给一条 trace，要能说清"这一波为什么选了经济而不是输出"。**不可解释的加权等于又一把黑箱尺子。**

### 25.6 裁决：③ **下一轮第一件事，无条件**；并把 `dpsAtWaveEnd` 打通进产物

③ 已连欠两轮。**下一轮它是第一个交付物，aging 工作在它之后。若一轮只能做 ③，就只报 ③。**

**理由不是它更急，是"欠着的东西永远被挤掉"这个模式本身有害** —— 它会让"下一轮做"变成一句空话。而且它只有半轮。

**并顺带把 `dpsAtWaveEnd` 打通进 `RunResult`**（逐波 DPS 字段）。**"唯一具名的读数"如果不进产物，就会被下一个人另写一份** —— 而那正是适配层前四次事故的成因（**重复映射**）。

### 25.7 ★★ 三条路径全部撞墙 —— 这是本轮最重要的结论

| 路径 | 撞墙方式 |
|---|---|
| **解析预测**（`dpsNeed`） | 度量有系统性乐观偏差：实测漏怪 75% 时它报"安全" |
| **标定门槛**（DPS 比） | 极差 **106.4pt**，且**对采样约定不稳定**（同数据 151.8% vs 222.6%）|
| **纯反馈** | **闩锁**：锁死在最后一个信号上，覆盖率反被饿死 |

⇒ **「漏怪」无法用任何"可算"的阵容指标稳定预测或控制**，因为它同时取决于射程覆盖、摆位、护甲类型、敌人构成、经济节奏 —— 一个高维、非线性、对细节敏感的系统。

**而一个人类玩家解决这个问题的方式是"判断"，不是"建模"**：看漏了几只、钱还剩多少、小偷够不够 —— 然后凭判断来回调。**他不需要归一化、不需要 aging 计数器、不需要标定门槛。**

> **⇒ 这是"需要把真人放进回路"的最强证据。**
> AI 的产出是真实的：证否了"数据不可通关"、抓出了心魔无界分裂、砍掉了三个死胡同旋钮。
> **但它验证不了"好玩"，而现在连"能赢"都验证不了。**

### 25.8 待决：可玩路径（真人试玩）

策划案 M2 的验收标准是「**15 分钟连续试玩无致命 Bug；试玩者能自主通关前 14 波**」——**那个"试玩者"应该是人。**

**现状**：`src/render/**` 有 `engine-dev` 建的可玩 `GameScene`，但它**既不消费真实数据**（适配层在 `balance` 侧）、**也不消费美术**（`art-proxy` 的 `SpriteSource` 未接线）⇒ **目前没有任何人打开就能玩的版本。**

**待主策划确认后启动接线工作**（跨 `src/render` / `src/art` / `src/balance` 三个 owner，需先定路径所有权与 `SpriteSource` 接入契约）。

| 3 | **反向对照**：限制为**只能建穿刺系（弓箭）** → 是否死得更早？ |

**若 1 显示漏怪波以城甲为主、且 2/3 方向成立 ⇒ 假设成立，修 AI 的类型选择。**

### 27.4 ★★ 主策划的假设（待验证）：**"便宜金币陷阱"第三次出现**

| 1 | `balanced` 从不研究科技 —— 清单末尾 **250 金**的扩建行被"买得起就买"每 tick 吃掉 |
| 2 | 漏怪时买 `worker`（`attack = 0`）—— **花光现金换零 DPS** |
| **3（本次）** | 不留限制时**优先买 200 金的弓箭手** —— 便宜的、看起来有用的、回不了本的 |

**三次都是"局部贪心把预算喂给了最便宜的东西"。**

`balance-eng` 早在第 6 轮自标过一个可疑量：

> 价值函数里「伤害→金币」的换算权重 **`DPS_GOLD_EQ = 400` 是启发式标定值，不是从文档读出来的。**

**⇒ 主策划判断（待验证）**：这个换算率**就是决定整个分配的那个自由参数**，而它**从未被标定过** —— 它决定"1 点 DPS 值多少金币"，也就决定 AI 在"买弓箭手（DPS）"与"买窃金塔（经济）"之间怎么选。

### 27.5 裁决：**否决"测人口利用率"** —— 数据已把它答掉

`balance-eng` 建议下一步测人口利用率（40–50 塔位只用了 8 个）。**但同一份数据里已有反证**：

```
gap 只攻城：21.7 座   gap 只魔法：23.7 座   heuristic 只攻城：24.7 座
⇒ 塔位【够用】，21–25 座都能建出来
```

**⇒ 塔位不是约束。** 约束在**动作选择策略**上：同一套塔位上限，不限制时只建 8 座、限制成攻城后建 21.7 座 —— **行为差 3 倍，瓶颈在选择逻辑而非容量。**

**裁决：不批准测人口利用率**（它会得出"塔位够用"，而我们早已知道）。

### 27.6 裁决：本轮主线 = 扫那个**从未标定的自由参数**

| 项 | 要求 |
|---|---|
| 扫什么 | `DPS_GOLD_EQ`（或价值函数里等价的"DPS↔金币"相对权重）的量级，跨 1–2 个数量级取 5–8 点 |
| 报什么 | **覆盖率 与 存活波数（两个都报）** + 窃金塔数 + 平均等级 + **每格的弓箭手数量** |
| 判据 | 是否存在某点**同时**逼近「30 波」与「≥65% 覆盖」 |
| **决定性的一问** | **整条曲线是跷跷板，还是存在双达标点？** |

**额外的机制验证**：若"弓箭手多"与"覆盖率低"强相关 ⇒ 直接印证"金币陷阱"。

**若曲线确实是跷跷板**，则得到一个比"调参失败"更硬的结论：**在当前投入产出比下，经济与存活不可兼得** —— 那时才轮到动数据（第 3 级或塔的性价比曲线），**而不是继续调 AI**。

### 27.7 裁决：修 `heuristic` 的"0 座窃金塔"，并入本轮

`heuristic` 窃金塔 **0.0 座**、覆盖率 **0.0%**、最高等级 **T0** —— **它一座窃金塔都不建。**

**⇒ 它那个 0% 是假数字**：不是"偷得少"，是"没有偷的塔"。

**必须修**，理由不是它不好，而是**它的数字出现在我们读过的每一张对照表里** —— 一个"没有经济"的策略被当作"经济差"的参照，会污染判断。

> **假 0 比没有数据更危险** —— 与铁律 8 的"空测量返回 0"同族。

**裁决：并入本轮做**（大概率是价值函数的排序/过滤问题），并**修完重跑对照表**看前几轮结论是否变化。

### 27.8 裁决：`allowedAttackTypes` 空数组语义**写成断言**

`balance-eng` 自报：空数组 = 不限（与 `undefined` 同义），**写进注释但没断言**。

**裁决：写成断言。** 理由：**"空集合"在直觉上等于"什么都不允许"，而语义是"全都允许"** —— 这正是本项目已踩五次的"同一表示两种含义"（`bounty` 绝对值/比率、`aura` 增量/乘区、`attackInterval` 频率/间隔…）。**反直觉的语义必须有断言钉住。**

### 27.9 裁决：① 的读数**口径必须标注**

① 读的是 `waves.json` 的**配置护甲**，不是实测出怪护甲（`RunResult` 无逐波出怪护甲清单）。

**可接受**（本期无中途换甲机制），**但结论旁必须标口径** —— 主策划本轮刚因"口径未标注"报错迁移处数（4 vs 23）。**口径不标注，下游就会当实测值读。**

## 28. M2 第十五轮：★★ 双稳态闩锁、以及「AI 当替代玩家」这条线的冻结

### 28.1 扫描结果：`DPS_GOLD_EQ` 扫 64 倍只产生 **3 种结果**

| `DPS_GOLD_EQ` | 窃金覆盖 | 均到波 | 窃金塔数 | 平均等级 | 弓箭手数 |
|---|---|---|---|---|---|
| 50 | 46.1% | 11 | 11.3 | T1.32 | 24.0 |
| 100 | 46.1% | 11 | 11.3 | T1.32 | 24.0 |
| 200 | 30.2% | 11 | 9.7 | T1.21 | 22.3 |
| **400（默认）** | 30.2% | 11 | 9.7 | T1.21 | 22.3 |
| 800 | 30.2% | 11 | 9.7 | T1.21 | 22.3 |
| 1600 | 28.2% | **12** | 8.0 | T1.25 | 24.0 |
| 3200 | 28.2% | **12** | 8.0 | T1.25 | 24.0 |

### 28.2 ★★ 结构性结论：**分配比例不由大脑决定**

```
两张扫描里【窃金塔数在所有取值下都是 9.7 座】（阈值跨越时也几乎不动）
只有【弓箭手数】在动（22.3 ↔ 24.0 ↔ 25.7）
⇒ 经济/输出的分配比例是 aging 硬分支决定的；大脑只决定"买哪一种输出"
⇒ 任何大脑侧权重（DPS_GOLD_EQ / SAFETY_WEIGHT / STEAL_WEIGHT）都无法移动分配比例
⇒ 【扫大脑权重找双达标点在结构上就是死的】—— 不是"还没找到那个值"
```

**这是本项目第三次"以为还没找到值、其实是结构表达不了它"**：① `dpsNeed` 估计器的乐观偏差 ② `DPS 比` 门槛的采样不稳定 ③ 本次。

**`SAFETY_WEIGHT` 扫描（"攻 ②"的实验）**：

| `SAFETY_WEIGHT` | 窃金覆盖 | 均到波 | 窃金塔数 | 弓箭手数 |
|---|---|---|---|---|
| **1（拆掉闩锁）** | **42.9%** | 11 | 9.7 | 25.7 |
| 2 | 42.9% | 11 | 9.7 | 25.7 |
| 3 / 6（默认）/ 10 | 30.2% | 11 | 9.7 | 22.3 |

⇒ **拆掉闩锁净得 +12.7pt 覆盖率、存活不降** ⇒ **主策划的裁决方向对、参数指错**（杠杆在"钉死不释放"的规则上，不在 `DPS_GOLD_EQ` 上）。

**闩锁机制**（`balance-eng` 定位，主策划确认）：`weightsFor` 在 `mix.output < 路数×2`（=4）时把 `dpsW` 钉到 `SAFETY_WEIGHT`，该条件**前期长期成立**；而经济与输出在价值密度上**近乎平手**（`T1 小偷 7 金/秒 × 1 = 7` vs `弓箭手 14 dps × 0.4 = 5.6`，再除以造价 `250/200` ≈ 相等）⇒ **一旦倒向输出就被锁住，参数只影响"翻与不翻"，不影响"翻到哪"** ⇒ 只有 2–3 态。

### 28.3 ★★ 裁决：**冻结「AI 当替代玩家」这条线**

`balance-eng` 给了两个选项（① 把分配升级为数据目标驱动的控制器 ② 承认无解去动数据）。**主策划两个都不批，提第三个。**

**理由：那条线的存在前提消失了。**

> AI 的用途从来是**在我们没有可玩版本时，替代人回答"能不能赢"**。
> **而现在可玩版本在发起人手上，它正在试玩。**

12 轮都产出了真东西（证否"数据不可通关"、抓出心魔无界分裂、砍掉三个死胡同旋钮、发现双稳态闩锁），**但"能不能赢"人 15 分钟就能答，而且人还能顺手答 AI 永远答不了的"好不好玩"。**

**⇒ 冻结**：不做控制器升级、不继续扫权重、不改 `SAFETY_WEIGHT` 默认值。
**⇒ 保留**「AI 当门禁」这条线 —— 这些是**真在干活**的，继续维护并保持绿色：

| 门禁 | 状态 |
|---|---|
| `solvability`（含两条负对照）| 权威 |
| 覆盖率定义性硬断言（`stolen ≤ wallet`）| 权威 |
| 变异覆盖 249 条（含"不该被映射"负对照）| 权威 |
| 出怪守恒（含分裂负对照）| 权威 |
| **实验后门断言**（见 28.6）| 权威 |
| 键登记 81/81（含陈旧双向检查）| 权威 |
| `survival-threshold` / `goldWorldPixels` 等 | **诊断**（非门禁，已在注释标明） |

> **理由不是"AI 没用"，是"不该继续造我们已经有替代品的仪器"。**
> 并且主策划自己也在这条线上反复判断失误（12 轮里指错参数、预测错覆盖率、误读单位）—— **人给一次读数比我再猜三轮便宜。**

### 28.4 裁决：`heuristic` 的覆盖率**继续标注为无效读数**，且不为此单开一轮

修后只从 **0.0% → 1.4%（1 座塔）**，根因是**结构**（纯大脑策略 + 无经济分支 + `dpsW` 闩锁），不是参数。

**裁决：接受其建议 —— 报告里继续标注其覆盖率为【无效读数】**，直到塔数 > 0 且稳定。**不为此单开一轮**（理由同 28.3）。

### 28.5 裁决：`SAFETY_WEIGHT` 默认值**保持 6**，不改

实验显示 `SW=1` 严格更好（+12.7pt 覆盖、存活不降）。`balance-eng` **没有擅自改**（正确）。

**裁决：保持 6。** 理由：
1. **只在 N2 上测过**（每值 3 局），而生产默认值改动是全局行为
2. **更权威的仪器（人）马上产出读数** —— 在它之前改默认值，等于用单难度测量覆盖一个即将到来的更可靠判断
3. **若 AI 线将来解冻，`SW=1` 是第一件该改的事**（记在此处，不会丢）

### 28.6 裁决：实验后门断言 —— **这 4 条做得对**

```
① 初值必须是默认（无残留）
② setter 设成默认值 == 从未调用过（hash 逐位相同 96d45fe47ba28383）✅
③ 负对照：dpsGoldEq 400 → 50 ⇒ hash 96d45f → deae1a，覆盖 29.7% → 47.1%
④ 负对照：安全权重 6 → 1 ⇒ 覆盖 29.7% → 45.1%
```

**没有 ③④，② 就是空话。** 这是铁律 8 第 1 条（负对照）用在**自己的测试基础设施**上。

`cloneSafeDefaults()` / `restoreDefaults()` + `finally` 还原（防状态泄漏给后续用例）亦正确。

**背景**：为扫描而引入的模块级可变状态（`setDpsGoldEqForExperiment`）是"同一事实两个来源"的另一种形态 —— **一个能被改的默认值**。断言把它钉住了。

### 28.7 裁决：`allowedAttackTypes` 空数组语义已加断言

`不限 wave=11/9 座 ｜ 空数组 wave=11/9 座 ｜ 只攻城 wave=9/22 座` —— **三态区分开了**，反直觉语义（空集合 = 全都允许）被钉住。

**经过**：
1. 该文件最初是 pnpm 交互提示的**原文**（`esbuild: set this to true or false`）—— 坏配置
2. **我"修"它时把键与值一起换成了 pnpm 10 的 `onlyBuiltDependencies`** —— **值确实错了，但键本来是对的**
3. 本地从不暴露：`pnpm install` 说 "Already up to date"（`node_modules` 已存在）
4. CI 全新安装直接中止：`[ERR_PNPM_IGNORED_BUILDS] Ignored build scripts: esbuild@0.21.5, esbuild@0.28.2`

> **这是"改对了症状、改错了部位"** —— 与 §23.1 的"按下标取难度"同族：**都是把一个看起来对的东西改成另一个看起来也对的东西，而真正的错误在别处。**
>
> **教训**：**修配置时先只改值；只有当值改对了仍然无效，才怀疑键。** 本次若只把值改成 `true` 而保留 `allowBuilds:`，一次就对了。

**正确形态的确认方法**（不靠猜）：`pnpm approve-builds --all` 会把它**实际写出**，原样抄回即可。该说明已写进 `pnpm-workspace.yaml` 文件头。

### 30.4 ★ 本地复现 CI 安装失败（省掉反复推 CI）

```powershell
robocopy . "$env:TEMP\gv-test" /E /XD node_modules .git dist
cd "$env:TEMP\gv-test" ; $env:CI='true' ; pnpm install --frozen-lockfile
```

**`CI=true` 是会改变 pnpm 行为的关键变量** —— 本地默认的 `pnpm install` 因 `node_modules` 已存在而永不暴露这类问题。**四种配置形态（`packages:["."]` / `package.json` 的 `pnpm` 字段 / `ignoredBuiltDependencies` / 加引号）都在这个临时目录里被逐个否证，没有一次需要推 CI。**

### 30.5 首次部署必须用**用户凭据**启用 Pages

`GITHUB_TOKEN` **不能**创建 Pages 站点：

```
X HttpError: Resource not accessible by integration
X Create Pages site failed
```

`actions/configure-pages` 的 `enablement: true` 在站点不存在时会尝试创建，但那需要仓库管理员权限。**解法**：用用户凭据跑一次

```powershell
gh api -X POST repos/<owner>/<repo>/pages -f build_type=workflow
```

（`build_type=workflow` = Source 选 "GitHub Actions"），之后重跑工作流即可。

### 30.6 部署侧的另外两条

**① `.gitignore` 必须保留 `src/art/out/`** —— 运行时会 `import` 那里的图集，被忽略就会构建失败。该目录**不在**任何"工具输出目录"的忽略之列（只忽略 `tools/art/out/`）。

**② 13 个文件是 CRLF，全部在 `balance-eng` 的路径里**（`src/balance/**` 11 + `tests/sim/**` 2），其余全仓纯 LF。`.gitattributes` 的 `* text=auto eol=lf` 在提交时统一（已核对 **索引里 `i/crlf` = 0**）。**工作副本未动**（离线 owner 的路径只诊断不修改）。
